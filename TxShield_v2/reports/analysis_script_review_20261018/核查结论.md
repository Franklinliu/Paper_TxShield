# contract_analyzer_thr321.py 核查结论

## 实际执行路径

1. full_processing_chain 第 3651 行先检索。
2. 第 3657–3660 行：仅当 XGBoost 存在、未跳过 RAG 且交易 JSON 非空时，在 LLM 调用前计算攻击概率。
3. 第 3663–3678 行：概率低于模型阈值则清空检索结果，设置 skip_rag=True；否则保留 RAG。
4. 第 3687–3691 行将概率传给提示词构建。
5. 当前有效 MessageManager.build_messages_with_prompt_template（843–942 行）依据是否存在检索上下文及概率是否 >=0.5，选择不同的系统指令。高风险且有上下文时强调攻击可能性；低概率或概率缺失时要求更保守判断。
6. 第 3702 行才调用 LLM；3705–3742 行直接返回 LLM 回答，没有 AND 规则或输出标签过滤。
7. analyze_contract 第 3843–3846 行会在推理后再次评分并附加元数据，但不会修改 answer。xgb_decision 在这里表示 use_rag/skip_rag 的模型建议，不能当作最终攻击标签，也不能总是代表实际使用了 RAG。

因此，本脚本实现的是 XGBoost 引导的检索上下文门控与提示词选择，而非 LLM 输出后的告警过滤。它与前次核查的 GitHub e7419320 提交中的纯后过滤逻辑不同。

## Table IV 的含义

“纯后过滤不能提高固定 LLM 输出的召回率”仍是正确结论，但不适用于此脚本：关闭 XGBoost 会改变 LLM 所看到的上下文/系统指令，预测可以从 0 变 1，也可以从 1 变 0，召回率没有单调约束。

若 wo_xgboost 通过传入 xgb_reranker=None 实现，现有提示词会把“没有数值模型”与“数值模型低风险”送入相同分支。因此该消融同时移除了检索门控及风险相关提示词选择，并不是仅移除最终过滤器。这可以解释为何 295 和 322 在机制上不再矛盾，但不能证明历史实验的配置就是如此。
