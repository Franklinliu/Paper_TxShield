## 核心结论

当前实现是条件执行的后过滤：仅对 LLM 判为 Attack 的交易计算 XGBoost 概率，概率达到阈值才保留 Attack，否则改为 Benign。LLM 判为 Benign 时不调用 XGBoost；无法解析时返回 Unknown，也不调用 XGBoost。

证据：src/txshield/contract_analyzer/pipeline/decision.py:21–36。对于有效二分类输出、已配置并正常工作的模型，最终攻击判定等于 LLM_Attack AND (p_XGB >= threshold)。

固定相同交易、标签及 LLM 输出时，最终 Attack 集合必为 LLM Attack 集合的子集。因此 TP、FP 均不能增加，召回率不能提高；精确率和 F1 可能改善，也可能下降。

论文 full-system TP322 对比 no-XGB TP295，不能由对同一批 LLM 输出单纯增加该过滤器产生。这不证明数据不真实，而是说明当前代码不足以解释两行之间的实验条件差异。需要逐交易的原始 LLM 标签、最终标签、XGBoost 概率/阈值及对应代码版本来判定原因。不能擅自归因为模型随机性或声称已解决。

## 数据流与异常路径

- rag_chain.py:161–180：先完成检索和 LLM 推理，再调用后过滤；传给 XGBoost 的是 system_input 交易 JSON。
- xgb_reranker.py:77–85：输入仅为交易数值特征，不包含 LLM 理由、置信度、标签或检索文本。LLM 标签仅决定是否执行 XGBoost。
- decision.py:39–50：原始 answer 保持不变，最终标签写入 final_prediction。读取 answer 的旧统计脚本可能忽略过滤结果；仓库本身不足以确认历史实验实际读取哪个字段。
- decision.py:30–31：手工构建链并传 reranker=None 时跳过过滤，Attack 原样保留。
- main.py:44–49：公开 analyze_contract 入口显式加载模型。加载发生在 LLM 推理前；缺失模型不会自动退化为纯 LLM，而是被 main.py:80–91 捕获并返回失败。
- extractor.py:45–49：非法 JSON 被静默转换为空对象，通常形成全零特征并继续分类，存在把输入错误当作有效交易处理的问题。
- xgb_reranker.py:51–73：阈值优先读取环境变量，其次阈值文件，无文件时为 0.5。历史实验阈值不能据此推定。

## 特征与训练

extractor.py:12–17 提取 14 个候选特征；transformer.py:4–14 删除索引 7、8、9、11，实际输入模型为 10 维：call_count、event_count、max_depth、unique_contracts、has_transfer、has_approve、has_flashloan、total_value（log1p）、unique_signatures、unknown_sig_count。当前训练和推理共享特征提取与变换函数；无法据此证明旧 pickle 模型也采用相同流程。

trainer.py:25–58 从指定训练目录分出验证集，用验证集选择阈值，再在全部训练样本上重训，最后评估测试集。代码没有验证训练和测试在交易、合约或时间层面是否隔离；不存在自动保证 420 个训练样本来源正确的机制。

独立 XGBoost baseline 的路径是 detection/inference/predictor.py:11–20 以及 scripts/evaluate_model.py:14–18，直接对交易分类，不经过 LLM。api/analyzer_api.py 是通用 predictor 适配器，不能仅凭 API 名称认定它调用完整 RAG 流程。cli.py 仅提供 preprocess/train 命令。
